# Shopbonus private merchant packages — candidate releases

These are candidate installation packages, not live-certified integrations. No credentials are bundled. Back up the test store first. Real provider acceptance remains NOT RUN. Build with `php scripts/build-merchant-packages.php`; ZIPs and SHA-256 manifest are in `public/downloads/integrations/`.

## PrestaShop 9

Upload `shopbonus-prestashop9.zip` in Module Manager and install **Shopbonus order bridge**. Select one shop in multistore context before configuring it. In Shopbonus configure the exact shop ID, verified HTTPS installation URL, shop timezone and restricted GET Webservice key for shop_urls/orders/customers/addresses/currencies/order_payments/order_slip. Enter the returned webhook URL and signing secret in the module. The secret is never redisplayed; rotate it in both places together.

Run `php /absolute/store/modules/shopbonus/bin/worker.php` every minute as the store's OS user. A nonblocking process lock prevents overlapping workers. Order, history, payment and credit-slip hooks queue only shop/order references; checkout performs no outbound request. Workers send signed ID notifications; Laravel performs the native authenticated read and mapping. Retries keep their event ID but refresh their HMAC timestamp. New changes during delivery remain pending. Order validation itself never proves payment. Slip-only refunds remain Unknown under the native mapper.

For banners, set the backend HTTPS origin and public `pk_...` key, enable the banner, authorize the storefront domain and publish the campaign in Shopbonus. The module uses the native footer display hook. Themes lacking that hook need approved theme work. Disable/uninstall the module to stop placement and remove its configuration/outbox; stop its cron and disconnect the backend connection separately. Backend records are retained under the existing retention policy. Payment, refund, multistore and install/uninstall behavior require a genuine PS9 acceptance run.

## OpenCart 4

Source contract reviewed against OpenCart **4.1.0.3**; OpenCart 3 and 4.0 are not claimed compatible. Upload **`shopbonus.ocmod.zip`** in Extensions → Installer, install that entry, then install/configure **Shopbonus order bridge** under Extensions → Extensions → Modules. Keep the ZIP basename: OpenCart derives the extension folder/namespace from it. Grant the standard module access/modify permissions only to the intended administrator.

This first package supports **default store 0 only**. Enter the backend connection's webhook URL/signing secret and the actual timezone used by order database timestamps, then enable the bridge. Run `php /absolute/store/extension/shopbonus/bin/worker.php` every minute as the store's OS user. The worker supports the native mysqli database driver and reads local `config.php`; the worker has no public HTTP entrypoint. The separately opt-in coupon read route below authenticates every request. Events queue references, not customer payloads. Disable the module before stopping cron; uninstall removes events, settings and outbox.

Order IDs/references/customer fields and native local timestamps are delivered using Shopbonus signed v1. **Order status does not prove capture, settlement or refund:** payment status remains Unknown, no paid/refund timestamp or refund cash is invented. Only unconverted EUR/USD/GBP amounts with exact two-decimal precision are mapped; other currency conversion/precision stays incomplete. Native admin order API, authoritative payment/refund provider extension, bulk recovery and seven-gate Connected remain unsupported. Do not call this a completed paid-order integration.

Package 0.2.0 also sends **product and coupon snapshots** (D-110): at most every six hours the same worker reads the default store's `product`/`product_description` (default storefront language, `config_language`) and `coupon`/`coupon_product`/`coupon_category`, and posts them as signed pages to the same webhook URL plus `/catalog` (topic `catalog.snapshot`). Prices are in the store's base currency (`config_currency`); times use the configured timezone. Snapshot synchronization exposes no read route on the shop. A snapshot only counts once every page arrived; a failure part-way keeps the previous snapshot. Coupon `date_start` is not sent (not-yet-active coupons appear active), and products without a name in the default language are skipped. Live store acceptance is NOT RUN.

Package **0.3.0** adds optional **authenticated live coupon reads**, disabled initially. Install the updated package and enable the matching checkbox in the module. Configure `store_url` (the exact verified HTTPS installation URL) and `timezone` through the backend connection create/replace-credentials API, then copy its newly generated signing secret into the module. Both sides must use the same actual database timezone and the store's `config_url` must match that HTTPS URL. Replacing credentials invalidates old signatures; update the merchant module afterward. Existing snapshot-only connections continue to synchronize snapshots, but require this configuration before live verification.

The fixed GET route `index.php?route=extension/shopbonus/module/shopbonus.coupon&code=...` requires a 60-second timestamp and HMAC over purpose/time/nonce/code. Its signed response binds nonce, observed time, store 0, URL, currency and timezone. It reads native coupon/history/product/category tables and enabled total extensions; it never applies a coupon to a cart. Do not cache the route or log its query/header contents. There are no browser credentials. Unsupported total extensions, per-customer/product/shipping constraints require review. Default OpenCart 4.1 installation and real-provider acceptance remain NOT RUN; local module SQL/authentication and Laravel flow tests use isolated fixtures.

Optional banner placement uses the native footer event and is disabled initially. Configure the public key/origin and enable it explicitly. Theme compatibility/editor acceptance remains NOT RUN.

## WooCommerce

Upload `shopbonus-woocommerce-banner.zip` using Plugins → Add New → Upload, activate, then configure Settings → Shopbonus Banner with the backend HTTPS origin and public `pk_...` key. Enable explicitly. Publish the campaign and authorize the storefront domain in Shopbonus. The plugin uses `wp_footer`; it adds no payment or editor authorization. Continue using WooCommerce's native signed order webhooks and restricted REST key for orders. Deactivation stops placement; plugin deletion removes its local settings. Multisite network-wide deployment/cleanup is not supported by this first package.

Plugin 0.2.0 loads `/embed/native-cart-v1.js` before the banner when WooCommerce is present, using WordPress's native Store API cart URL. Deploy that reader alongside the backend public embed. Checkout/account pages are excluded. Store API session totals drive progress; invalid/stale data falls back to static terms. Classic/Blocks notifications and bounded polling refresh the cart; custom themes should dispatch `shopbonus:cart-invalidated` after completed mutations. Two-decimal currencies only; no headless cart tokens, checkout attribution writes or genuine installed-store acceptance are claimed. Details: backend `docs/banners/NATIVE_CART_ADAPTERS.md`.

## Shopify

`shopbonus-shopify-theme-source.zip` contains **Theme App Extension source**, not a Shopify merchant-uploadable ZIP. Copy `extensions/shopbonus-banner` into the existing authorized Shopify app project, preserve that app's identity and run its Shopify CLI checks/deployment. Do not create a second app or change the registered app's scopes as part of this source import.

After installing that app on the authorized test store, the merchant enables **Shopbonus Banner** in the theme editor's App embeds, enters the public banner key/backend HTTPS origin, and saves. Campaign publication and storefront-domain authorization remain separate Shopbonus actions. Disable the embed and save to stop placement. Uninstall through Shopify and disconnect the backend connection to end integration access. The extension targets body, never checkout. The loader is idempotent and rejects non-HTTPS/credential-bearing origins. Theme CLI validation, app deployment, merchant activation and real storefront/editor acceptance are **NOT RUN** without the authorized app project and store.

## B93 — Native session-cart progress (candidate package update, 2026-11-07)

Deploy the updated backend `/embed/native-cart-v1.js` with these packages. Enabled packages load it before the renderer; no private cart values are embedded into cacheable page HTML or sent to ShopBonus. The browser reads only its own cookie-bound native session. Integer totals and explicit supported two-decimal currencies are required; unknown/sub-cent/malformed/mismatched values fall back to static terms. These are native integration assets, not changes to the ShopBonus frontend application.

- **PrestaShop9 package0.2.0:** update the module normally, retain the existing per-shop banner configuration, allow its native footer hook and `module/shopbonus/cart` GET through the merchant's cache/CDN as private/no-store. The native context's cart must match its cookie, shop and currency, with group price visibility enabled. GET returns only the custom cart-source schema/total/currency, never IDs/items/PII. The module declines unavailable carts; it does not fabricate a zero. Other methods return405. Native updateCart/updatedCart events and bounded polling refresh progress.
- **OpenCart4.1.0.3 package0.3.0:** update extension files and re-register the extension's install events through the authorized administrator (existing CREATE IF NOT EXISTS outbox/settings are retained; do not uninstall/drop them). Keep default store0, module and banner enabled. The added event attaches `X-ShopBonus-Cart` JSON to the **existing** `common/cart.info` response, using native totals and presentment currency conversion. It adds no new catalogue/shop read endpoint, reads no HTML prices and does not change signed six-hour product/coupon snapshots. Cart-info responses must bypass shared caches. Price-hidden guests get no snapshot. Native custom theme code can notify `shopbonus:cart-invalidated` after completed mutations; otherwise visible-page polling detects changes.
- **Magento Open Source / Adobe Commerce2.4 self-hosted/PaaS module0.2.0:** deploy normally with DI compilation and cache updates. At the exact store view, enable the separate storefront banner flag, set the public HTTPS ShopBonus origin/key and allow that origin in storefront CSP. Private section `shopbonus_cart` is read through Magento's existing `customer/section/load` route; no new native route or quote/customer ID selector exists. The native session quote/store/presentment currency must match. Checkout/customer/sales/payment pages emit no scripts. Native change notifications and polling refresh the section. Disable the storefront flag/remove the module through normal deployment to stop both reader and renderer. Adobe Commerce SaaS/headless storefronts cannot run this PHP module and remain unsupported by this adapter.

Installed framework execution, theme/CSP behavior, native store upgrade/disable/uninstall and genuine customer add/remove/quantity/coupon/currency/recovery evidence are NOT RUN.
