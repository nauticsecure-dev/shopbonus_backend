## Hassan: AI workflow

All four operations are under `/api/v1/workspaces/{workspace}/banners/{banner}/ai-requests`, with normal verified workspace membership and `offers.manage`. Support sessions cannot access them. Insights additionally requires `orders.view` for creation, reads and review; an editor without order access cannot see another staff member's insight evidence.

1. `POST` with `{kind: designs|insights, request_key: UUID}` queues one request (202). Retry the same workspace/key/actor/campaign/kind to retrieve that run without another quota reservation. A conflicting reuse is409. Disabled configuration503; daily cap429. Poll `GET .../{run}` or list `GET .../ai-requests` (20/page).
2. Completed runs contain exactly three distinct proposals with `editable_config`, known evidence references and server-rendered hypotheses. A failed run returns a fixed failure code, never provider error bodies. Treat all proposals as unverified hypotheses, not measured uplift.
3. Design proposals change placement/colors/font; existing heading/subtitle/terms, CTA, merchant image/logo, devices, frequency and triggers stay intact. These are editable structured content/style/image/CTA fields, not flattened generated raster images. The model never receives those private text/URL/asset fields. The frontend maps these existing config fields to its editable layers.
4. Insights samples up to1000 complete provider-confirmed paid/partially-refunded EUR orders within90 days (at least10). Only sample count/net amount and existing banner aggregates leave the server. No customer/order IDs, customer details, raw logs, order payloads, URLs or secrets. Unknown categories, products and repeat-customer metrics are not invented. Linked offer reward/fee/minimum are computed by existing MerchantFunding; e.g.1000 reward +300 fee =1300 cost. No linked offer means no cost estimate, not a fabricated zero.
5. Insights can add minimum timing/cart conditions while preserving existing restrictions. Invalid configurations, including excessive trigger depth, fail closed. Hypotheses are rendered from schema-validated choices; the provider has no free-text channel to claim measured uplift, successful actions or new offer terms. Evidence and source configuration/model/revision/offer-version snapshots are immutable. Live metrics may change after capture; sample evidence describes that captured sample, not current results.
6. `POST .../{run}/review` with `{decision:accept, proposal:0..2, note}` creates a separate private draft and returns its public ID; `published:false`. Reject uses `{decision:reject,note}` and prohibits a proposal index. Only one append-only review per run. Changed source draft or offer version conflicts409 and requires fresh generation. Existing commercial, funding and offer checks apply when a human later publishes/schedules/resumes. AI cannot launch/publish, pay, reserve vouchers or change reward terms.

For a same-campaign A/B test, the merchant can use an accepted draft's editable config with the existing source-draft PUT/revision workflow, then explicitly publish it as another version before starting the experiment. A private AI draft is never automatically treated as a published variant.

## Hassan/plugin developer: experiments

- `POST .../banners/{banner}/experiment` takes `{control_version: integer|null, variant_version:integer, variant_bps:1000..9000}`. Both versions must already be published versions of that same live campaign; null control is a true no-banner holdout. One active experiment per campaign. Requires offers.manage and commercial activation. Version snapshots and allocation cannot be edited; stop then launch another experiment for a different test.
- `GET .../experiment` requires offers.view and returns the latest experiment with per-arm assignments, impressions/clicks, confirmed paid orders/converting visitors and net EUR revenue. No statistical significance or causal uplift is claimed. `POST .../experiment/stop` stops new assignment; normal published config resumes. Starting/stopping is audited. Pause suppresses the normal public config; publish/rollback while active conflicts409 to preserve pinned versions.
- With applicable analytics consent, generate an opaque UUID for this shop's visitor/session. `POST /api/v1/banners/assignments` with `{key,visitor_key,consent:true}` from the allowlisted merchant Origin returns per-campaign arm/token/version. Do not send user/account identifiers. The raw UUID is never stored; the DB keeps shop-scoped HMAC plus an unpredictable stable random arm. Retries/concurrency return the same assignment for that experiment. Tokens expire after30 days. No consent means no assignment or experimental banner.
- On withdrawal, call the same endpoint with the same UUID and `consent:false`, discard local tokens, and stop sending them into events/checkout. It revokes matching assignments; they cannot be resurrected. A new explicit consent can use a fresh UUID. This is a browser/session capability, not proof of identity or authentication.
- Fetch published config with `assignments[CAMPAIGN_ULID]=ASSIGNMENT_TOKEN`. Assigned responses are private/no-store; do not cache them in a shared CDN. Unassigned experimental campaigns and holdout controls are omitted. Other campaigns work as before. Never render a draft or send editor tokens through this route.
- Send `assignment_token` on every experimental event. Server validates campaign/version/arm/consent/time, using the existing event ledger and deduplication. Holdout has version0 and permits only `eligible`; no holdout impression/click is accepted. A dismissal remains a dismissal. Ordinary events now also require an existing published version; fabricated version numbers are rejected.
- Pairing exchange and every editor read/write now recheck active, verified user membership and offers.manage; removal/suspension/revocation immediately invalidates existing capabilities.

Public browser view/click reports remain client-reported observations, not independent proof of visibility or purchase. The renderer must still implement ≥50% visibility for ≥1 second, frequency, device rules and graceful fallback.

## Verified order linkage and honest results

The signed Shopbonus webhook v1 format accepts `order.attribution.assignment_token`. The installed integration must propagate the consented assignment from storefront/cart through checkout into authenticated provider order metadata, **including holdout orders**. A browser redirect or eligibility event is never payment confirmation. The existing signature verification, event idempotency and payment-state engine remain authoritative; the first valid same-shop assignment is retained on the normalized order.

Experiment results count complete paid/partially-refunded EUR orders whose actual paid timestamp falls between assignment creation and expiry (and before consent revocation, when applicable). Late authenticated callbacks may arrive after the experiment stops; their original assignment window still applies. No token means unattributed, no guessed match. Multiple orders remain separate revenue records; converted visitors are distinct assignments so conversion rate cannot exceed100% from repeat purchases. Refunds reduce net revenue; fully refunded/unpaid/cancelled states are excluded.

The existing generic, WooCommerce and Shopify adapters map these Shopbonus-defined metadata fields: generic `order.attribution.assignment_token`, WooCommerce `meta_data` key `_shopbonus_assignment_token`, Shopify `note_attributes` name `shopbonus_assignment_token`. The installed module/cart bridge must persist those fields only with applicable consent. All three mappings are fixture-tested; live propagation and other platforms remain unverified. See [WooCommerce order metadata](https://developer.woocommerce.com/docs/apis/rest-api/v2/orders) and [Shopify order attributes](https://shopify.dev/docs/api/admin-rest/latest/resources/order). Missing mapping is a verification limitation, not evidence of zero conversions. No statistical uplift/significance or rollout winner is automatically calculated or published.
