# Controlled backend staging execution

B84 supplies execution plumbing, not completed E2E acceptance. It adds no HTTP endpoint and executes no AI-generated commands. The original 175-check source, full frontend inventory, genuine provider subruns and independently reviewed staging proof remain incomplete. `requirements/QA_RUNNERS.json` deliberately remains unmapped; no fictitious approved script is registered.

## Configuration and review

Set `QA_STAGING_RUNNER_ENABLED=true`, `QA_STAGING_URL` to the exact HTTPS staging origin and `APP_RELEASE_SHA` to the deployed full Git SHA. The Laravel environment must be `staging`; production is refused. Use a shared lock-capable cache across scheduler nodes (`QA_STAGING_LOCK_STORE` defaults to database; scheduler onOneServer also requires its default cache to be shared), run Laravel's scheduler and retain private evidence storage. The deployed Git metadata/source must be readable. No credentials are accepted in the origin. Origin configuration must point to a disposable authorized staging environment; the runner cannot infer production from a hostname.

Commit reviewed PHP entry points under `scripts/qa-runners/` and register their exact SHA-256 in `requirements/QA_RUNNERS.json`. Registry shape:

- `schema_version: 1`, `state: reviewed`, `review_reference`: actual Git review/analysis-plan reference.
- `runners`: 1–10 unique entries, each with `id`, `path`, `sha256`, `triggers` (nightly/weekly/after_deploy), `timeout_seconds` (1–300), and nonempty `tests` (at most2000 entries). Each test records exact `key`, integer `version` and positive `min_assertions`. Keys must map to current approved phpunit/postman/browser cases; AI proposal/manual metadata is not executable coverage. Duplicate keys across selected runners are refused. Existing reviewed registries without these mappings must be updated/reviewed before execution.

The registry itself and selected script bytes must match the actual deployed Git commit. A label/hash alone cannot authorize changed/untracked source. Review dependencies and fixture cleanup as part of the script review; hash verification does not prove script semantics or truthful provider evidence. Entry points are trusted code executing with staging deployment privileges, not a security sandbox. They must not bootstrap RefreshDatabase against staging, change a production endpoint, expose credentials, leave child processes running or execute model-supplied code. Use dedicated least-privilege staging identities/test tenants. No automatic source generation or approval is implemented.

Each child receives `QA_RUN_CONTEXT`, a private JSON file containing exact build, trigger, target origin and backend discovery diff, and `QA_JUNIT_PATH`, a new private output path. Context now includes `execution_plan`, keyed by runner ID, with explicit `allowed_tests` and `required_tests`. For `after_deploy`, every added/changed/removed backend endpoint/component must have approved coverage and every impacted approved case must belong to a reviewed runner for that trigger. Missing mappings stop before any child executes. All discovery snapshots on that exact build are combined, so failed attempts cannot erase impacts by rescanning. Only runners with required tests execute. When no code diff is known, all reviewed mapped tests are required rather than claiming configuration/dependency changes are harmless. Nightly/weekly always require every test registered for their selected runners. This enforces known backend mappings, not exhaustive frontend or semantic discovery. Generate genuine JUnit with positive assertions and real failures; do not emit a canned passing report. Required provider/browser evidence remains bound to actual results via existing Quality Center APIs and independently reviewed acceptance mappings.

The service runs PHP via an argument array with no shell. All selected sources are checked before any runner executes and checked again immediately before each process. A shared 3,700-second lock excludes all triggers. The registry allows at most 3,000 seconds of process time in one batch. Each process has a 1 MiB output ceiling; stdout/stderr are discarded rather than published as potentially sensitive evidence. JUnit uses the existing bounded parser, no external entities, and is retained as sanitized result records. A nonzero process cannot turn green JUnit into PASS: its passing rows are imported as blocked. Timeout, missing/oversized reports, source drift, skipped/mocked/failed results and unavailable infrastructure fail the command. Temporary context/report files are deleted; scripts must retain authentic evidence through the evidence service, not in temporary output paths.

Reports must contain every required test, no duplicate/unregistered keys and the registered minimum assertion counts. Case approval/version/executable-source checks run again on report import; revoked or revised cases cannot qualify using an earlier plan. A mismatched report retains its assertions but passing rows are imported as blocked, not PASS. Ordinary CI imports without a reviewed execution plan retain their existing regression-only semantics. Automatic imports have no human executor and unknown cases stay draft. They cannot satisfy independent acceptance by themselves. Existing manifest requirements still enforce all 175 checks, 60 provider subruns, exact frontend inventory, source mappings, current build, minimum assertions, authentic request/database/screenshot/provider evidence and independent review. The command always invokes that gate after successful execution; no `--skip-gate` switch exists. Missing proof exits nonzero and `release_approved` remains false. Final release approval is separate.

## Entry points and deployment limits

Laravel registers staging-only nightly02:00 and Sunday04:00 schedules, gated by the enable flag and shared scheduler locks. These are real command schedules, separate from production health probes. Existing `QaSchedule` API records do not authorize arbitrary executable commands or replace the reviewed registry.

After deploying the exact recorded build, invoke `scripts/qa-after-deploy.sh` from the backend root **before promotion** and require its zero exit code. It invokes `shopbonus:qa-staging-run after_deploy --sha="$APP_RELEASE_SHA"`; never append `|| true`. The shell hook is supplied, but no external staging deployment pipeline, scheduler process, branch protection or provider credentials have been installed/configured by this change. The senior deployment owner must wire this step into the actual promotion job. A local synthetic runner test is not evidence that this deployment integration ran.

Local regression tests execute real temporary PHP scripts and a tiny isolated Git repository; they cover impact context, exact source matching, wrong environment/build/origin, disabled/unreviewed execution, lock exclusion, timeout/output/report failures, nonzero process imports and the mandatory closed gate. They do not call staging/providers or establish genuine browser journeys. Frontend discovery, Quality Center UI and documentation portal shell remain outside the backend implementation scope and incomplete.

B82 follow-up: `shopbonus:qa-staging-run` now invokes both the original acceptance gate and `shopbonus:cms-content-check`; either nonzero result blocks success. The recommended CMS contract/runner/source bytes must be committed on the configured deployment before evidence can qualify. Runner executable paths are explicitly restricted to reviewed PHP files under scripts/qa-runners; requirements manifests are data, never executable entries. Actual23 content executors/frontend discovery and deployment wiring remain unmapped/unexecuted; see docs/cms/BULK_AND_COVERAGE.md.

## B86 deployment adapter

`.github/workflows/qa-staging-gate.yml` is an opt-in reusable/manual GitHub workflow. It uses an existing trusted self-hosted runner labelled `shopbonus-staging`, the `staging` environment and configured environment variable `SHOPBONUS_STAGING_ROOT` (absolute deployed backend root). No checkout/install/reset is performed. The supplied `deployment_sha` must be full lowercase40/64hex and match that root's actual Git HEAD before the existing hook runs. Laravel still independently requires staging, enablement, explicit HTTPS origin, lock-capable cache, reviewed committed registry/scripts and configured exact SHA. Never register this runner for untrusted PR workloads or point its root at production.

The actual deployment workflow must call this reusable workflow after deploying staging and require its successful job before promotion (a dependent job, not `continue-on-error`). This adapter does not install a self-hosted runner, deploy code, configure credentials or connect an unknown external promotion pipeline. It remains NOT RUN against genuine staging. Missing registry/original175/provider/frontend proofs still block both independent gates; a green execution plan is not release approval.
