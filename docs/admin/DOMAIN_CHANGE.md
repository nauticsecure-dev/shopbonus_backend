# Verified-domain change

Ordinary `PUT /api/v1/workspaces/{workspace}/business-profile` autosaves retain `409 domain_locked` when a verified domain would change. A cached model cannot bypass the lock: the service re-reads the webshop under lock before checking ownership. Foreign workspaces retain audited404 concealment (not403); preserve the recorded acceptance clarification.

A verified-domain change is an explicit privileged reconciliation, not a silent profile edit. A deployment-console operator must authenticate through deployment access, obtain the owner's authorized change case and identify the responsible verified active Super Admin:

```bash
php artisan shopbonus:change-verified-domain <WEBSHOP_PUBLIC_ID> \
  --actor=<VERIFIED_ACTIVE_SUPER_ADMIN_PUBLIC_ID> \
  --expected-domain=<CURRENT_VERIFIED_DOMAIN> --website=https://new-domain.tld \
  --reference=<AUTHORIZED_CHANGE_CASE_ID> --reset-verification
```

Console access is the authorization boundary; actor public ID is attribution, not login. The server re-reads actor authority, locks the shop and compares expected-domain to current proof. Missing confirmation/options, revoked/unverified/inactive actors and stale/no-op domain changes fail. Suspended/rejected shops require their separate authorized lifecycle workflow first; this command cannot lift restrictions. Only already-verified domains can use this process.

The target is normalized to a public hostname and canonical `https://hostname` profile URL (path/query removed). Case references are bounded nonempty200-byte identifiers without control characters; do not paste secrets or private customer records. The transaction clears business confirmation, ownership proof/current verified domain and approval, sets awaiting_verification, supersedes pending/submitted challenges and disconnects every current webshop integration through ConnectionManager. That wipes local credentials, advances credential generations and clears current connection observations. It does not erase orders, signed agreements, historical verified attempts, wallet records or integration history. Existing review flags remain; they cannot be silently cleared by changing a domain.

Replays using the old expected-domain fail after the first reset and cannot repeatedly increment generations. Reconfirm the business profile, prove ownership of the new domain and pass the existing lifecycle/current-agreement rules. Old proofs cannot be reused. New challenge creation rechecks the current domain under lock; completion checks the current profile domain against the observed challenge. A duplicate domain still follows the existing manual-review policy.

Create and verify fresh integrations against the new verified domain. Local disconnection does not uninstall provider apps, delete remote webhooks or revoke every external API credential. The senior/operator must remove old remote installations/webhooks and rotate provider credentials as appropriate. Pending old-generation callbacks/jobs cannot establish new integration readiness. Do not reactivate disconnected connections to reuse old verification. Historic signed agreement snapshots remain intact; the existing agreement service decides whether the current version needs acceptance, without inventing revised legal terms.

Coupon generation remains **UNSUPPORTED**: current connectors expose native coupon reads/verification, not an authorized idempotent coupon writer. Step2 can paste/import existing platform codes; import success is not checkout acceptance. No coupon is generated by this domain workflow, and coupon-write capability is not promoted from order connection/read success. A future provider write boundary needs explicit write scopes, durable idempotency/uncertain-outcome reconciliation, exact immutable offer-term mapping, failure recovery and genuine create/checkout acceptance evidence. Frontend localization and approved-reference comparisons remain outside this backend change; deployed browser/autosave/queue/import/activation acceptance remains NOT RUN.
