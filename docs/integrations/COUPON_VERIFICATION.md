# Native coupon configuration verification (B71)

Automatic `provider_check` now supports WooCommerce plus **Shopify, BigCommerce legacy v2 coupons, Ecwid, Lightspeed E-Series, Wix, Magento and Squarespace, narrowly unrestricted Shopware 6 promotions, OpenCart 4.1 live module reads and unused single-shop PrestaShop rules**. Native lookups reuse the existing connector transport, verified store/domain identity, current credentials, pause/disconnect gates, bounded response parsing, TLS/SSRF protection and provider permission handling. They perform reads only; Shopify uses a fixed GraphQL query, not a mutation. No installation, coupon creation, checkout application or redemption is performed.

`verified` is a point-in-time native configuration match. It is **not** proof that a particular customer/cart can apply a coupon, nor that it was redeemed. That requires an actual provider-backed checkout/order journey. The new native results explicitly return `evidence_scope: native_configuration_not_checkout_or_redemption`. Manual confirmation retains its distinct `manually_confirmed` status. Imports alone remain merchant-verification-required.

## Comparison and unknown values

New adapters compare native currency, exact integer fixed minor units/percentage basis points, minimum spend, current enabled/start/expiry state and remaining global usage against current offer terms or the historical voucher's frozen terms. Fractional percentage values not exactly representable in basis points are not rounded into a match. Nonreusable codes must be configured for one global use; exhausted codes mismatch. Finite reusable capacity and per-customer restrictions need manual review. Expiration must cover an issued voucher's expiry, otherwise the offer end or applicable redemption window.

New adapters do not invent a maximum-discount cap. An offer with a cap remains manual when that cap cannot be proved natively. Thus an active fixed-value merchant reward can verify, while a capped percentage merchant reward generally requires merchant review on these providers. Product/category-specific offer constraints, unsupported discount kinds, requested combination behavior and unknown restrictions remain explicit manual conditions. Known differences return `mismatch`; missing proof does not become a successful match. Only safe normalized configuration fields and constraint names enter the result/event; raw codes, customer targeting lists and native payloads do not.

Before persisting a new native observation, a transaction locks and rechecks the code, source credentials/store binding, verified domain/ownership and the current offer version/terms. An in-flight edit or rotation returns `sync_error` with `verification_context_changed`; draft terms use canonical serialized dates and the same version-before-offer lock order as the existing editor. Historical checks use the frozen voucher snapshot, remain linked to that voucher's event history, and do not overwrite the inventory code's current validation status. No wallet, obligation, purchase, allocation, claim or redemption status changes occur. Existing WooCommerce comparison behavior is retained in this boundary; this change does not certify every WooCommerce restriction or repair its pre-existing maximum-order-versus-discount-cap semantics.

Other platforms retain `unsupported_integration` and controlled manual confirmation even where catalog coupon reads exist: a lossy catalog snapshot does not establish full coupon verification. No coupon-write/banner/connected capability is promoted by these reads. Native configuration can change after observation; recheck it and independently exercise checkout before relying on delivery readiness.

## API and evidence

The existing authorized `POST /api/v1/workspaces/{workspace}/codes/{code}/platform-validation` endpoint is reused, with `{"mode":"provider_check"}` and optional historical `voucher_id`. Existing permission, rate-limit and error semantics remain; no new route, migration or credentials are introduced. Native observations are stored in existing voucher events with `provider_check`, configuration scope and safe differences/unknown constraints.

[Eleven actual local HTTP responses](../qa/B71_COUPON_VERIFICATION_HTTP_CAPTURE.json) cover four native matches, mismatch, unknown context, foreign404, employee403, unauthenticated401, invalid-mode422 and an in-flight offer edit rejected as `verification_context_changed`. Reproduce with `python3 scripts/capture-native-coupon-verification.py`. The private temporary SQLite/storage/key/router are cleaned afterward. Actual Laravel HTTP authentication, authorization, comparison and persistence run; **provider transport and DNS are synthetic fixtures** installed only in the disposable router. These are not genuine provider or checkout acceptance. No production behavior reads the harness's `X-Capture-*` controls.

Tests include active fixed-value offers, frozen historical terms, native identity/scopes/pause, missing or conflicting codes, incomplete pages, malformed values, restricted/expired/exhausted coupons and tenant/permission denial. Actual credentialed provider acceptance remains **NOT RUN** for all new adapters. The senior configures read scopes and executes installation/configuration/checkout/redemption journeys separately.

Official source contracts: [Shopify exact-code lookup](https://shopify.dev/docs/api/admin-graphql/2026-10/queries/codeDiscountNodeByCode), [Shopify buyer contexts](https://shopify.dev/docs/api/admin-graphql/2026-10/unions/DiscountContext), [BigCommerce legacy coupon list](https://docs.bigcommerce.com/developer/api-reference/rest/admin/content/marketing/coupons/get-coupons), [Ecwid coupon search](https://docs.ecwid.com/api-reference/rest-api/discounts/discount-coupons/search-discount-coupons), [Ecwid coupon fields](https://docs.ecwid.com/api-reference/rest-api/discounts/discount-coupons/get-discount-coupon). ## Remaining provider boundaries — 2026-11-07

The cross-platform task is still **PARTIAL**, with three external evidence requirements. Adding a `CouponLookup` implementation that always invents missing fields or returns verified from a signed partner assertion would not close them.

- **Lightspeed C:** the official [PHP SDK](https://github.com/SEOshop/API-PHP-Client/blob/master/src/WebshopappApiClient.php) confirms GET `discounts` and `discounts/{id}`, not `discountcode`. The provider field documentation returns HTTP403 in this environment. Need the approved response schema for amount/type, dates, usage, tax/shipping/product scope and discount-rule combinations before implementing comparison. Owner asked for a documentation link/redacted documented response; none supplied yet. The adapter remains unsupported rather than guessing field names.
- **Mijnwebwinkel:** existing signed partner order bridge does not establish native coupon configuration. Need approved partner coupon-read documentation and authorization/store identity contract. No native partner API schema or credentials are guessed. Owner asked for documentation or an existing authorized integration; none supplied yet.
- **CCV:** live currency and coupon readers/comparison are now implemented. The [documented native resource](https://demo.ccvshop.nl/API/Docs/) does not establish combination policy or complete historical usage. It returns known mismatches or `merchant_verification_required`, never a fabricated successful match. Need additional authoritative evidence contract before full automatic verification.

**PrestaShop** now joins native `order_cart_rules` history rather than treating remaining quantity as original allocation. A complete empty history in one observed shop proves this narrow unused configuration; any recorded history, multishop or competing active rules stays manual. No extrapolation of original capacity from remaining + partial counts.
