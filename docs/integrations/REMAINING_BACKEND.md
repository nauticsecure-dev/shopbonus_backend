## Shopify authorization

Server settings: `SHOPIFY_OAUTH_ENABLED=false`, `SHOPIFY_CLIENT_ID`, `SHOPIFY_CLIENT_SECRET`; fixed read_orders/read_products scopes and APP_URL callback `/api/v1/integrations/shopify/oauth/callback`. Senior configures an approved app/redirect and protected-data access locally. Existing manual signing secret/token support remains.

POST `/api/v1/workspaces/{workspace}/integrations/shopify/oauth` accepts a canonical shop_domain in a normal authenticated browser session with integrations.manage/CSRF. State is random256bits, stored as a hash with actor/session/workspace connection, app config, credential generation and ciphertext fingerprint; expires10minutes. Callback is a browser GET, independently verifies Shopify query HMAC, rejects duplicate query keys and stale timestamp, rechecks fresh membership/session/config and consumes state before code exchange. Fixed HTTPS token endpoint uses form encoding and expiring offline credentials. Native shop identity/domain/scopes must pass before encrypted token storage; authorization resets readiness and never posts orders.

Refresh has a per-connection distributed lock, bounded HTTP and stale ciphertext/generation guards. Ordinary same-grant renewal preserves authority/readiness; changed app config/scopes/expired refresh authority requires reauthorization. Transient network failures preserve the old pair for retry. Manual rotation/disconnect still invalidates all outstanding proof. Keep the app secret consistent with configured webhook signatures. Signed app/uninstalled performs a native revocation check outside row locks before disconnecting/removing credentials. A still-valid current installation survives replay of an old signed uninstall. Unknown/manual or transient proof never authorizes revocation. Privacy app lifecycle is **not implemented**; existing privacy workflows remain necessary.

### Shopify webhook provisioning (B23i, 2026-10-29)

Opt-in `SHOPIFY_WEBHOOK_SETUP_ENABLED=false`. Requires an OAuth-approved connection (`oauth_authority`), a verified store, and a signing secret equal to the configured app client secret (Shopify signs app-subscription deliveries with it). Seven fixed 2026-10 topics: ORDERS_CREATE, ORDERS_UPDATED, ORDERS_PAID, ORDERS_CANCELLED, ORDERS_FULFILLED, REFUNDS_CREATE, APP_UNINSTALLED. Callback is always the server-owned connection webhook URL (HTTPS, no port/query/userinfo), format JSON, no filter/includeFields; no caller GraphQL or URI.

Per topic: cache lock 90s; native `webhookSubscriptions(first:100, topics:[topic])` listing first (truncated list refused). An existing exact-callback JSON subscription is reused; duplicates or filtered/field-restricted ones need operator review; subscriptions to other endpoints are never touched. Before `webhookSubscriptionCreate`, an append-only `integration.webhook_create_intent` audit row commits under a connection row lock with generation/authority/store/token/domain rechecks. After creation the listing is read back and `integration.webhook_subscription_observed` is recorded only if the same ID is present and the generation is still current. If a create outcome is unknown (timeout, lost acknowledgement, rotation), later runs list first; if the subscription is still missing, they refuse with `provider_hook_outcome_unknown` + `intent_id` until an operator inspects Shopify and runs the single-topic inline review. Provisioning never changes readiness or ingests orders.

After a committed OAuth grant (enabled only), seven `ProvisionShopifyWebhook` jobs (3 tries, 75s timeout) are queued after commit. A synchronous queue or dispatch failure is audited as `integration.webhook_dispatch_failed` and never relabels/rolls back the grant.

```sh
php artisan shopbonus:provision-shopify-webhooks <CONNECTION_ULID>                      # queue all 7 (async queue required)
php artisan shopbonus:provision-shopify-webhooks <CONNECTION_ULID> --topic=ORDERS_PAID --inline
php artisan shopbonus:provision-shopify-webhooks <CONNECTION_ULID> --topic=ORDERS_PAID --inline --review-intent=<AUDIT_ID>
```

Use `--review-intent` only after confirming in Shopify that no subscription exists for that topic and callback. Shopify's TOML-declared app subscriptions are an alternative that senior configuration may prefer; this path does not inspect or replace them. Not verified against a live store.

Official review: [standalone app authorization](https://shopify.dev/docs/apps/build/authentication-authorization/authenticate-standalone-apps), [GraphQL LineItem](https://shopify.dev/docs/api/admin-graphql/2026-10/objects/LineItem), [webhookSubscriptionCreate](https://shopify.dev/docs/api/admin-graphql/2026-10/mutations/webhookSubscriptionCreate), [webhookSubscriptions](https://shopify.dev/docs/api/admin-graphql/2026-10/queries/webhookSubscriptions); Wix [Search Orders](https://dev.wix.com/docs/api-reference/business-solutions/e-commerce/orders/orders/search-orders).

## Durable bulk discovery

Operator command:

```sh
php artisan shopbonus:sync-integration-orders <CONNECTION_ULID> --since=2026-10-27T00:00:00Z --until=2026-10-28T00:00:00Z --request=<UUID>
php artisan shopbonus:sync-integration-orders --drain --limit=25
```

Fixed UTC window, maximum90days, UUID payload binding, generation/domain/exact-store binding, one bounded page per job, cursor hash journal and deterministic per-run/per-order recovery UUIDs. Each order uses existing canonical native recovery with purpose `reconciliation`; ordinary bulk traffic cannot replace the operator verification sample. Completion waits for all associated recoveries to succeed. Failed/stale recovery is not success. Expired reading leases resume; known failures require investigation and a new request UUID after correction. Previously staged pages remain durable, but a failed run is never advertised as complete.

Automatic discovery is disabled. `INTEGRATION_SYNC_ENABLED=true` additionally requires explicit comma-separated `INTEGRATION_SYNC_CONNECTIONS` public IDs. Scheduler drains each minute and considers opted-in stores every5minutes; windows overlap120seconds and failures cool down15minutes. Offset/cursor APIs over mutable remote data are bounded observations, **not an atomic store snapshot or a guarantee against all concurrent remote changes**. Webhooks plus overlapping scans and operator historical rescan remain necessary. No provider URL from a response is followed. No automatic provider writes/refunds.

## Exact line snapshots and migration

The pinned JSON reader preserves decimal/exponent lexemes before PHP decoding, so money never passes through a binary float. Scientific notation is preserved as text and rejected by Money rather than rounded. Woo line totals are discounted/ex-tax; Shopify line totals explicitly include code discounts and retain provider shop-money basis. All item IDs, optional product IDs/SKUs, integer quantities and exact minor amounts are bounded; truncated/malformed/mixed-currency collections remain null. `null` means unavailable/incomplete, `[]` means observed empty. Reward-eligible amount is null until an independent approved rule establishes it; line snapshots never create rewards or FX.

Current projection and append-only event snapshot are encrypted separately. Missing later details preserve the current projection but do not fabricate an incoming history snapshot. Order list/show adds line_items under existing orders.view/tenant permissions. Other provider detailed line mappings remain incomplete.

Migrations180000/190000/200000 add one-time authorizations, durable discovery/page journal/recovery purpose and encrypted line snapshot columns. Quiesce old workers/intake during rollout/rollback. Back up encryption keys and preserve historical source evidence; never manufacture bindings on rollback/reapply. Main/production schema application is recorded separately in HANDOFF; never infer it from tests. D-089 affiliate timing is unchanged.
