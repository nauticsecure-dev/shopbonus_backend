# Support connectivity: correlated receipts (B89)

Backend-only correction of HTTP receipt bypass and unrelated worker completion evidence. No migration, provider/model call or frontend implementation. Existing support processing uses the default connection/queue; probes now explicitly freeze that same connection/name. Deploy with a shared, lock-capable cache (database/Redis) visible to HTTP, scheduler and workers, and restart workers after code/configuration changes.

## Private client receipt protocol

1. Authenticate the administrator's own private notifications channel using the existing broadcasting authorization endpoint. Subscribe and wait for subscription success before starting a probe. The channel is `private-shopbonus.user.<public-user-id>.notifications`.
2. POST `/api/v1/admin/ai/connectivity/browser-probe`. HTTP returns only `probe_id`, `channel`, `event` and `expires_in:60`. It does **not** return the acknowledgement challenge.
3. Receive `support.connectivity.browser_probe` on that private channel (Echo's custom-event syntax needs the leading dot). Its payload is `{probe_id, nonce}`. Match the public probe ID to this start; do not acknowledge a different/reordered event.
4. POST `/api/v1/admin/ai/connectivity/browser-probe/<probe_id>/ack` with JSON `{"nonce":"<event-only challenge>"}`. The historical OpenAPI path placeholder remains `{nonce}`, but its path value is now the public probe ID. Body `nonce` is the independent secret from Reverb. Old clients echoing the former HTTP nonce must update; retaining that compatibility would retain the security bypass.

Cache stores only the challenge SHA256. A per-administrator atomic cache lock protects latest-probe replacement and single-use acknowledgement. Wrong/foreign/expired/replayed/superseded/configuration-mismatched challenges fail404 without consuming a legitimate receipt. A missing/malformed body fails422; lock contention fails409. Current active Super Admin authority is revalidated server-side. A non-Reverb broadcaster fails503 rather than pretending to send; broadcast errors invalidate that pending probe. Start keeps its existing diagnostics rate limit. Responses are private/no-store.

Monitoring reads browser evidence only for the requesting administrator. A new start supersedes their older success; other administrators cannot inherit it. Reverb connection/origin changes invalidate observations. States are pending, expired, failed, acknowledged, stale or not_measured. A receipt older than15minutes is stale. Scheduled/CLI reads without an administrator do not claim browser receipt. `browser_probe_scope` explicitly describes **authenticated client receipt**, not a browser engine, deployed page listener, every client or worker availability. A trusted client can be Node; this protocol cannot prove which runtime received the event.

## Queue-worker receipt correlation

The scheduler stores the latest random nonce, dispatch timestamp, connection/name and a hashed queue-configuration fingerprint under an atomic lock. It explicitly dispatches `ProbeSupportWorker` to that connection/queue. The queued job takes its actual connection/name from Laravel's running Job context; manually calling `handle()` without that context does not record proof. Older serialized jobs default their missing configuration to empty and cannot qualify.

Completion must match the latest nonce, original timestamp, queue target, current queue configuration (including the resolved database/Redis target) and cache namespace. Wrong/out-of-order/duplicate completions cannot replace a new pending observation. Processing must occur within180seconds of dispatch; evidence is current only while that dispatch remains within180seconds and timestamps are ordered/non-future. Until the latest job completes, status is pending for90seconds then not_processed. Changing the connection configuration/name invalidates previous proof, returning not_measured. Sync/null drivers explicitly prove no asynchronous worker. Only matched processed receipts expose latency; prior/unrelated work never fills that field.

## Executed local evidence and remaining acceptance

`python3 scripts/verify-support-receipts.py` creates private temporary SQLite/storage/cache/queue and ephemeral credentials/accounts, starts actual Laravel HTTP and Reverb processes, dispatches the real probe and executes a separate `queue:work database --queue=receipt-proof` process. A Node WebSocket client obtains genuine private-channel authorization, subscribes, starts the HTTP probe, receives its event-only challenge and acknowledges via HTTP. It checks HTTP-only rejection, another admin, replay, per-admin visibility,401/403/422, cache-lock409, stopped-broker503 and limiter429. Both services and temporary files are removed afterward. Reverb wildcard origins are confined to this isolated synthetic process; no deployment origins are changed.

[21 actual HTTP exchanges](../qa/B89_SUPPORT_RECEIPTS_HTTP_CAPTURE.json) include request IDs/cache headers, a real pending→processed worker transition and the synthetic WebSocket protocol result. Unit tests separately exercise expiration, supersession, changed Reverb/queue configuration, wrong timestamps/queues, old worker completions and manual job invocation. Synthetic accounts and consumed one-use challenges are explicit; no real credentials/customer data are captured. The initial unit test mistakenly treated Queue::pushed entries as arrays; fixed to use their actual job objects. Scoped static analysis prompted a real class-default compatibility fix for old serialized jobs; no suppression was added.

The **frontend listener remains unimplemented** under this backend-only assignment. No real browser engine/page, cookie-session/CSRF lifecycle, deployed workers/Redis, TLS/proxy, network interruption/reconnect or independent staging/provider acceptance is claimed. Those journeys still need genuine environment evidence. The new contract and Node harness make backend receipt verification reproducible without implying frontend delivery is complete.
