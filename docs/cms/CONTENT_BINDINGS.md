# Saved content bindings and pinned component media

B80 extends B79 media using existing CMS pages, locales and immutable revisions. It introduces no table or migration. Scope is PARTIAL: existing page content is inventoried, not frontend code, FAQ records, email templates, tenant media or every editable source in the entire product.

## Authoritative source identity

The protected bindings endpoint reads a single draft or exact same-page/locale immutable revision. Each saved leaf has its path, current value, content kind, canonical translation eligibility and source metadata: global scope, explicit null webshop, page public ID/key, locale, draft/revision identity, version and content SHA256. Empty arrays, null and non-text values are included. The media pin metadata is represented by media usage rather than mistaken for translatable text. Draft IDs combine page public ID and locale; immutable revisions retain their public ID.

Values are derived on demand from the authoritative snapshot. There is no asynchronous index that can silently lag a save. Bindings paginate by field offset; send the returned hash with every subsequent request. A changed snapshot returns409, requiring restart. Historical content is immutable. These bindings establish saved backend source identity, not exhaustive UI reachability or “zero forgotten functions.” New sources need explicit inventory support rather than silently inheriting coverage.

## Usage-specific recipe pins

All existing page create/save workflows accept optional `content.media_recipes`, a map of exact image-field paths to recipe ULIDs, with at most200 entries. For example, pin `body.content.1.attrs.asset_id` to a ready recipe belonging to the asset referenced at that exact path. Structured paths ending in `_asset_id` and rich-document `asset_id` references are recognized. Recipe and preserved-original checksums must bind to the same asset; all three breakpoint derivatives must be ready. Missing/foreign/incomplete/unbound pins fail422. No active asset-level pointer is substituted for an omitted pin.

The map lives inside existing versioned content. Ordinary optimistic draft saves, immutable publication and exact revision restore preserve the chosen usage recipe. A later asset recipe creation/restore does not change old page versions. Existing content without pins remains valid and uses its existing compatibility URL; the manifest exposes `recipe_not_pinned`, without claiming responsive usage is already connected. Changing a referenced asset requires updating/removing its old pin in the same draft save. The API does not infer an equivalent crop for a different original.

## Component-context preview and usage discovery

The protected media-preview endpoint returns the exact saved content, including text, buttons and overlays supported by that page schema, alongside each media usage path/component, recipe, derivative dimensions/checksum/state/URL and stable compatibility URL. Suggested viewport widths are desktop1440/tablet768/mobile390; they are recommended preview inputs, not proof of approved design breakpoints or actual browser rendering. Clients must render this saved content with their real component and choose pinned derivatives. No frontend renderer or screenshot comparison is implemented here. Artifact metadata does not prove storage health or visible delivery; B79 restore performs the separate integrity check.

The media-usage endpoint scans bounded batches of100 source records. Query `source=draft` and `source=revision` separately, and follow every `scan.next` until null. Revision scans include history, even when a revision is no longer published. An empty result page with non-null next is not evidence that an asset is unused. The scan scope explicitly excludes other content models, tenant assets and client code. It must not authorize global deletion or a product-wide replacement claim. No physical file deletion, archive or “replace everywhere” mutation is added by this checkpoint. A concurrent save can change usage between scan pages; full management mutations will need their own reviewed/fresh concurrency boundaries.

All three read APIs require current active Super Admin authorization and return private/no-store responses. No arbitrary tenant selector, source path, storage path or original download is accepted. Originals remain protected by B79. Unknown source/page/locale/revision yields404; invalid query/pins422; stale binding hash409. Existing authentication/role/rate-limit/CSRF/error policies remain in force. There are no new mutations besides the optional pin metadata on existing protected CMS save routes.
