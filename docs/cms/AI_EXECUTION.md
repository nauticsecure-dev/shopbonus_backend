## Configuration and monetary enforcement

AI stays OFF by default. Configure `CMS_AI_ENABLED`, API key/model, database `cms-translations` worker and a positive `CMS_AI_DAILY_BUDGET_MICROS` (integer micro-euros, at most1,000,000,000). Zero disables execution even if request queuing is enabled. `CMS_AI_VERIFIED_PRICING` is a server-managed JSON object with exact model, currency EUR, nonempty review/quote reference, absolute valid_until date (YYYY-MM-DD UTC, no more than31days ahead), verified model context_tokens (at most2million), input_micros_per_million and output_micros_per_million (positive bounded integers). No provider price or exchange rate is assumed. The senior deployment owner must verify model limits and conservative EUR rate/FX ceilings covering the quoted validity period. Configuration labels cannot prove provider pricing truth; these are execution guards under those reviewed assumptions, not invoice reconciliation.

Immediately before each provider call, the worker locks the UTC-day quota and proposal, reserves the cost of the **entire configured model input context plus maximum output**, and records its pricing/output/cap snapshot. This intentionally over-reserves relative to typical short text. Serialized payload byte bounds plus overhead must fit the reviewed input allowance; no automatic truncation. Rates use integer arithmetic with upward rounding. Reservations remain held after success, rejection, timeout or ambiguous failures; they are not refunded from smaller reported usage. Duplicate job delivery never repeats execution. Changed credentials or provider failure do not grant another monetary allowance. Budget exhaustion/unconfigured pricing fails the proposal before networking; poll error_code for the distinction from request-count quota429.

Valid provider usage is recorded as a configured-price estimate, not settled cost. Usage exceeding the frozen model/output profile marks the day's spending blocked. Concurrent workers serialize on the same day row; execution-day accounting applies even when a request waited overnight. Daily request quotas remain a separate control. API calls specify default service tier, text-only input, no tools, store:false, max_output_tokens and disabled truncation. There is no unbounded fallback/retry model. The deployment owner must monitor failed proposals, held reservations, actual provider invoices and pricing expiry before changing caps or re-requesting work.

## Legacy endpoints and section scope

The existing four legacy `/admin/content/.../ai-suggest` routes retain `data.suggestions` and `applied:false`, adding `proposal.id`, `status`, `section`, `poll_url` and `independent_review_required`. Queued/processing work returns202 with an empty suggestions array. Clients must poll the existing canonical proposal endpoint; terminal states return200 with their explicit status. A ready proposal can expose the scoped suggestion fields, but still requires independent review to apply through the canonical flow. The old `CMS_AI_SUGGEST_ENABLED` configuration does not enable a parallel caller.

Only bindings inside the requested section enter that provider call and receive replacements; other text, structure, references, recipe pins and links stay unchanged. Optional focus is treated as untrusted copy preference, never as authority to introduce facts. Source/target revisions, source hash, configured model and section/focus participate in coalescing/idempotency. Different sources cannot reuse an idempotency key. An old pre-budget proposed result cannot silently satisfy a new execution; use a new key/proposal rather than bypassing provenance. API clients must respect source conflicts and show pending/failed/review-required states. No frontend polling implementation is included here.

## Independent language and meaning review

`POST /api/v1/admin/cms/suggestions/{suggestion}/review` requires a recently confirmed active Super Admin session. The reviewer must differ from the proposal creator and explicitly attest both actual target-language correctness and preserved meaning, with a note. This is a human review workflow, not an automatic language detector, independent second-model validation or proof of a95% live-model quality threshold. Reviewers must actually inspect the source/proposal and be competent in the target language; the server cannot establish that from boolean fields.

A single immutable review binds reviewer, target locale, source hash and exact proposed-content hash. Wrong locale, changed source/target, duplicate review or self-review is refused. A negative language/meaning verdict rejects the proposal; request a new proposal after correction. Apply rechecks source/target, current actor/reviewer/creator authority, the accepted independent review, proposal hash and budget provenance. Revoked reviewers, modified proposals and legacy/unreviewed records cannot apply. Apply saves only a draft; publication remains a separate authorized, revision-protected action. Manual content editing remains possible and is not labelled AI-reviewed merely because someone copies text into a normal draft.

Apply migration `2026_11_04_110000_add_cms_ai_budget_and_reviews` before deploying code. Existing quota/suggestion rows retain history; old proposals without monetary provenance require a new proposal. No wallet or affiliate accounting changes. B79 media migration/worker remains separate.
