## 2. Domain rules that MUST remain correct

- One user identity can act as consumer, prospective merchant, workspace owner or workspace staff; Super Admin is privately provisioned. Signup intent confers no elevated privileges. Workspace membership and permission are server-owned; each webshop is an isolated workspace (`webshop_id`) and users may hold different roles in different shops. Consumers retain a global identity and central consumer wallet. Owner summary endpoints combine only authorized shops without double-counting.
- Each merchant's business profile, ownership verification, versioned agreement, connection, orders, staff, offers, voucher codes, reports and audit events are scoped to that shop. Super Admin support access requires auditable, time-bound, purpose-bound impersonation/assistance; never reuse merchant credentials.
- Ecommerce integrations must verify webhook signatures, scopes, external order IDs, paid state and refunds; do not treat a browser redirect, JavaScript event, 'success' page or unverified webhook as proof of payment. Normalized orders are unique per provider/shop/external reference and state transitions are safe under retries and out-of-order delivery. Store original event identifiers and evidence. Providers may have different capabilities; report `Connected`, `Limited`, `Setup Required`, `Error`, etc. honestly.
- Answer24 owns the calling process, agent actions, marketing communications and approved reminders. Shopbonus owns order eligibility, secure signed handoff, scoped API, voucher code reservation, single-use claim, consumer account verification, redemption/claim status and audit. Call only for verified paid and eligible orders with a valid phone and lawful basis; cancellations/refunds suppress pending outreach. Group multiple qualifying orders for a consumer/webshop inside the specified one-hour window into one contact opportunity, with idempotent callbacks. Never build a second dialer or assume order receipt grants consent.
- There are **two distinct voucher flows**: (A) merchant-funded customer reward attached to an eligible verified purchase, often redeemed on a later purchase, including Answer24-origin free claim links; (B) a consumer using central Shopbonus wallet credit/points to buy a discount voucher, with an optional Mollie top-up. Do not conflate them. Keep a single canonical voucher/code inventory and issuance system with typed origin. Codes may be unique or explicitly reusable subject to merchant/offer rules. Reserve, issue, redeem, expire, dispute, replace and reverse only through guarded transitions with immutable snapshots and auditable events. Issuance is not the same as verified merchant-side redemption.
- Wallet data is authoritative in immutable, append-only entries. A consumer wallet is virtual redemption credit/points, nontransferable and never cash-withdrawable. Merchant funding wallets are distinct from consumer wallets. Use integer cents/points and declared unit/currency, precise rounding, available/reserved/spent balances, DB transactions, row-level locking, unique idempotency keys and compensating entries; never permit negative spendable balance or duplicated debits/credits.
- Merchant direct-funded economics from the board: consumer reward is funded by merchant; **Shopbonus fee 30% ON TOP OF the reward amount**, not on order value. A €100 order with a €10 reward implies €10 customer value and €3 platform fee, or €13 merchant obligation, subject to applicable contract/rule. Support merchant funding via Mollie iDEAL and accounting/invoicing via Moneybird only where configured/authorized. No silent cross-shop settlement or double billing.
- Affiliate networks include Daisycon and TradeTracker using verified, authorized adapters; map programs, tracking links, conversion IDs/statuses, rules, commission, reversals and reconciliation without double-rewarding an underlying conversion. A click alone never awards spendable rewards. The board **conflicts** on immediate credit versus approval-gated credit: **DO NOT silently choose**. First inspect current business rules, log decision as `OPEN-AFFILIATE-CREDIT-TIMING` and ask the owner for a definitive policy before enabling spendable money/credits in that affected path. Until then build flexible tested status transitions, avoid accidental early credit, and proceed with independent work. Network rejection must not silently undo already redeemed value; corrections require explicit auditable policy and no unapproved negative balances.
- Mollie shortfall checkout: calculate from an authoritative quote, reserve wallet funds and inventory, create provider payment idempotently, verify provider status server-to-server, fulfill exactly once, release reservations on failed/expired/cancelled payments, reconcile paid-but-unfulfilled states and handle refunds/chargebacks with compensating entries. Never issue a usable code on a browser redirect alone. Confirm seller-of-record, VAT and refund policy before live money flows.
- Answer24-origin voucher claims: signed and expiring handoff, single-use claim/verify, reserve code at authorized handoff, **90-day** claim window, allowed reminders at days **30/60/80** under Answer24's lawful communications policies; ensure no duplicate sends and revoke/suppress after claim/expiry/cancel. Shopbonus does not send its own sales calls.
- Tracking and live banners: backend manages merchant-specific campaign/config revisions, publish/rollback, safe public configuration, installation diagnostics, consent-aware event ingest, signed editor pairing permissions, first-party permitted click IDs, experiments/holdouts, attribution to verified paid orders and honest reporting. **Do not implement browser editor/overlay/embed frontend** in this assignment. Success-page hits ≠ paid orders; attribution ≠ causal lift. Prevent cross-shop PII leaks. Reconcile provider refunds and order changes.
- Super Admin API: scoped dashboards, users/workspaces, offers, voucher lifecycle, orders, wallets/merchant funding, provider health, affiliate reconciliation, audit/security, exceptions, CMS, settings and customer support. Use live, measured aggregates; don't fabricate KPIs or label order starts as paid sales. Enforce robust permissions even on global search and exports.
- Consumer profile & content: authorized profile details/images, secure email change, email OTP verify/reset flows, consent/preferences, published multilingual NL/EN CMS/legal revisions, cookie preferences, favorites/categories, support tickets. Mandatory account/security messages remain separate from optional marketing consent.
- AI support: Shopbonus-specific customer/merchant support only, not a general chatbot SaaS. Backend authenticates user/scope and selects allowlisted read-only Laravel tools. AI drafts must be independently verified against current authoritative data before display; one targeted additional retrieval attempt, never unlimited retry. Only claim actions after verified Laravel success. Restrict cross-tenant data exposure; feedback must flow to human review and regression cases. Build backend endpoints, queues, safe realtime events, settings/knowledge versioning and evidence audits. Choose a real supported OpenAI model via configuration; do not hardcode an unverified model ID.

## 3. API engineering requirements

Implement consistent versioned REST endpoints and OpenAPI examples, preserving existing path compatibility. Design routes only after auditing what is present. Use authenticated `/api/v1/me`, `/api/v1/workspaces/current/...`, `/api/v1/consumer/...`, `/api/v1/admin/...`, `/api/v1/public/...`, `/api/v1/ai/...` conventions as appropriate. Names in Trello are proposed contracts; check compatibility before renaming anything. Public data must not reveal stock secrets, voucher codes or PII.

Specify request schema, response schema, resource visibility, permission, tenant scope, rate limits, idempotency requirements and error cases for each endpoint. All financial endpoints expose integer minor-unit amounts plus unit/currency, never floats. Handle 401/403/404/409/419/422/429/500 with stable JSON shape and request/correlation ID; never leak resource existence across tenant boundaries. Prevent IDOR, CSRF, XSS through stored fields, SSRF in integration URLs and unauthorized exports. Encrypt provider credentials; rotate where supported. Mask secrets, payment details and customer contact data in logs. Rate-limit provider ingestion and expensive reports. Use queues, backoff, dead-letter or failure queue, circuit breakers and admin alerts for failures. Ensure transactional outbox/idempotent dispatch or equivalent where DB and external side effect coordination is needed.
